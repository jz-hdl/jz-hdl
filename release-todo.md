## About this document

This is a structured release-readiness review of the `jz-hdl-dev` project against a notional 1.0.0 target. The project is broken into 14 logical groups; each group is scored independently 1–10 against criteria appropriate to its type, with a short rationale and a list of items that must be completed before 1.0.0. An overall project score with weighting rationale is written in Step 3.

Scoring scale (applied uniformly to every group):

| Score | Meaning |
|-------|---------|
| 1 | Broken or missing |
| 3 | Fragile, many gaps |
| 5 | Usable but rough |
| 7 | Solid, minor gaps |
| 8 | Production-ready with minor rough edges |
| 9 | Spec-complete and polished |
| 10 | Shipped-quality |

## Top 1.0.0 Blockers (cross-cutting)

Consolidated from every group. These 10 items are the ones whose resolution would most move the overall score upward. Ordered roughly by how much they gate a 1.0.0 call.

1. **Fix the known correctness-engine bugs.** `GBIT_INDEX_OUT_OF_RANGE`, `SBIT_INDEX_OUT_OF_RANGE`, `GSLICE_INDEX_OUT_OF_RANGE`, `SSLICE_INDEX_OUT_OF_RANGE`, `CONST_CIRCULAR_DEP` are all marked "Not Tested: Bug" in `pipeline/rule_coverage.md`. For a language whose value proposition is compile-time correctness, shipping 1.0.0 with 5+ known bugs in the rule engine is a contradiction. (Groups 3, 7)
2. **Reconcile rule-coverage drift across the whole compiler.** `compiler/src/rules.c` has ≈387 entries vs. ≈375 documented in `pipeline/rule_coverage.md`. Worse, Group 3 confirmed that several rules marked "Unimplemented" are actually implemented (`AMBIGUOUS_REFERENCE` at `driver_project.c:1711`, `LATCH_SR_WIDTH_MISMATCH` at `driver_assign.c:1218`/`:1234`). The coverage map is wrong in both directions and cannot be trusted as a maturity signal. Walk every rule and reconcile. (Groups 1, 3, 4, 7)
3. **Resolve the 4 untested tristate-transform rule conditions.** `TRISTATE_TRANSFORM_MUTUAL_EXCLUSION_FAIL` (Bug), `PER_BIT_FAIL`, `BLACKBOX_PORT`, `SINGLE_DRIVER` (all Unimplemented) are emitted by `ir_tristate_transform.c` (lines 1610, 2444, 1838, 2697) but not exercised by any test. Tristate lowering is one of the project's flagship features. (Group 4)
4. **Fix `soc`/tang_nano_20k synthesis FAIL and add example builds to CI.** It's the only failing row in `examples/status.md`, and `soc` is the only example exercising tristates + BUS abstraction end-to-end — losing it hides systemic issues. `scripts/run_examples.sh` already exists but is not invoked by `.github/workflows/ci.yml`, so `status.md` will drift after its 2026-04-11 timestamp. (Groups 5, 12, 14)
5. **Decide the IR JSON stability story.** `ir_serialize.c` writes JSON with version `"0.1.0"` but there is **no deserializer** (`jz_ir_load`/`jz_ir_deserialize` returns 0 hits compiler-wide). Either implement a loader so `--ir` becomes a round-trippable component API, or explicitly document in `ir.h` that the JSON is a debug artifact with no stability guarantees. 1.0.0 cannot silently promise both. (Group 4)
6. **Wire `gw5a-lv25-mg121-c1-i0` into runtime or delete it.** The chip JSON is a complete 748-line file, its header is generated by the CMake glob, but `compiler/src/chip_data.c:41–48` does not `#include` it and `k_builtin_chips[]` at `:50–59` does not list it. A dead chip file is worse than no file. (Group 8)
7. **Fix `docs/getting-started/installation.md` broken paths.** References `cmake -S jz-hdl` instead of `cmake -S compiler`, and a non-existent `jz-hdl/tests/blink.jz`. This breaks the first-contact experience for new users — the single most user-visible documentation bug in the project. (Group 13)
8. **Fix `scripts/release` and add an automated release workflow.** The release script uses BSD `sed -i ''` syntax, which silently fails on GNU sed (Linux CI runners) — the release pipeline is therefore broken on Linux. There is also no GitHub Actions release workflow for binary artifacts; binaries are currently manual. For a 1.0.0 release, both must be fixed. (Group 14)
9. **Decide the Viewer and VSCode extension release story.** Viewer is a 2,466-line ImGui/SDL3 app with live-reload and measurement cursors, but it is JZW-only, not in any build integration, and absent from README and CI. VSCode extension is functionally solid but lacks icon, README, `repository`/`bugs`/`homepage` metadata, CHANGELOG, and end-to-end verification. Each is a "tech preview" unless integrated — pick a path and own it. (Groups 10, 11)
10. **Close critical example feature-coverage gaps.** `examples/coverage.md` catalogues 21+ zero-coverage rows including SR latches, hardware `*`/`/`, `=z`/`<=z`/`=s`/`<=s`, `@new[count]` array instantiation, CASE `x` wildcards, `RESET_ACTIVE=High`, `EDGE=Falling`/`Both`, and several intrinsic classes. The team already knows what's missing (the file lists suggested new examples). Build at least the top 3 (tri-state/INOUT compact, width-extend demo, hardware `*`/intrinsic demo). (Group 12)

**Secondary items that did not make the top 10** but are flagged in the group sections: path-security rules marked "Not Testable", JZW spec still "Draft", `jzw-specification.md` x/z semantics undocumented, CLI `--jitter`/`--drift` undocumented in README, `examples/README.md` missing, VitePress installation paths broken (subset of #7), 15 "Dead code" rules, dead unit-test file structure, dark-gray diagnostic color on black terminals, no contributor onboarding doc (`CONTRIBUTING.md`/`RELEASES.md` absent).

## Overall Score: 6 / 10

**How this score was reached.** I read all 14 completed group sections, then did the calibration pass described in the plan.

**Calibration adjustments applied in Step 3:**
- **Group 7 (Diagnostics, Rules, and Reports): 8 → 7.** The agent correctly identified that the *infrastructure* (diagnostic.c, report modules, CLI integration) is at an 8 level — clean, well-designed, zero TODO markers. But the criteria explicitly include rule-registry health, and 41 of 387 rules are problematic (7 Bug, 15 Unimplemented, 15 Dead code, 4 Suppressed) — 10.6% of the registry. A registry with 10% defects is not "production-ready with minor rough edges" no matter how good the surrounding infrastructure. Adjusting to 7 aligns this group with IR/Backends/Simulator stringency.
- **Group 11 (VS Code Extension): 7 → 6.** The code is solid — LSP launch, 37 directives, sensible settings — and matches G9 CLI/LSP on 7 when judged on implementation alone. But packaging gaps are substantial: no `icon`, no `repository`/`bugs`/`homepage`, no `README.md`, no `CHANGELOG.md`, moderate `npm audit` finding, end-to-end activation never verified. For a distributable artifact at 1.0.0, those are not "minor rough edges". 6 = "between usable but rough and solid with minor gaps" — the code is 7-tier, the packaging is 5-tier, the average lands at 6.
- **Group 14 (Build & CI Infrastructure): 8 → 7.** CMake/CTest/validation script quality is at an 8. But the release pipeline has a **silent BSD-sed portability bug** (`scripts/release` broken on Linux), there is **no automated binary-release workflow**, `scripts/run_examples.sh` is **not in CI**, and the project version is still `0.1.7`. These gaps compound. 7 matches the IR/Backends/Simulator tier more honestly.

**Distribution:** ten 7s, two 6s, one 8, one 4. Unweighted mean: (6+8+6+7+7+7+7+7+7+4+6+7+7+7)/14 ≈ **6.64**. Weighted mean (critical-path groups 1–9, 12–14 weighted 2×; secondary groups 10, 11 weighted 1×): ≈ **6.77**. Both sit between 6 and 7.

**How the groups were weighted.** For a 1.0.0 call on a compiler/HDL toolchain, the critical-path groups are the language spec, the full compiler (frontend → semantic → IR → backends → simulator → diagnostics), CLI/LSP, chip data, examples, docs, and build/CI. The Waveform Viewer and VS Code Extension are valuable but do not gate the language's 1.0.0 — a user could install the CLI and use jz-hdl without either. I weighted those two at 1× and the rest at 2×.

**Why 6 and not 7.** Three things pulled me down from the weighted-mean 6.77 to 6:

1. **Known correctness bugs in a correctness language.** `GBIT/SBIT/GSLICE/SSLICE_INDEX_OUT_OF_RANGE` and `CONST_CIRCULAR_DEP` are marked "Bug" in `pipeline/rule_coverage.md`. The project's core differentiator is catching silicon bugs at compile time — shipping 1.0.0 with 5+ rules in the compile-time-check engine marked "Bug" is incompatible with the value proposition. A score above 6 would have to argue these bugs are minor, and I don't think they are.
2. **Coverage-map drift undermines all other maturity claims.** Group 3 showed the rule-coverage map is wrong in *both* directions — some "Unimplemented" rules are implemented, some implemented rules are undocumented, and the total count is ~12 off. This means any reader (user, contributor, or Step 3 reviewer like me) cannot trust any maturity statement in the repo without verifying it in code. That's a meta-problem that reduces everyone else's trust in every other score.
3. **The team's own version number is `0.1.7`.** Per `compiler/CMakeLists.txt:3`. I calibrate toward the team's own judgment when there is no compelling reason to deviate. A 6/10 at 0.1.7 implies a credible path to 1.0 — a 7/10 would imply 1.0 is within reach, which the Top 10 blocker list contradicts.

**What would move the score up.** Resolving items 1–3 of the Top 10 (correctness bugs, coverage-map drift, tristate-transform rules) would move most compiler groups from 6→7 or 7→8, which would lift the overall to 7. Adding items 4–5 (CI example coverage, IR JSON stability decision) would push it to 7.5. Items 6–10 together plus binary-release infrastructure would make 1.0 defensible at 8.

**What the score means.** 6/10 = "between usable-but-rough and solid-with-minor-gaps". Accurate for a mature, production-quality-in-many-places 0.1.7 project that has a clear path to 1.0 but is still carrying known bugs in its safety features. Not a score of despair — a score of "real work, all of it visible in the tree, most of it small but consequential".

## Groups

### 1. Language & Specification — Score: 6 / 10

**Paths owned:**
- `specification/jz-hdl-specification.md` — core language semantics and syntax
- `specification/simulation-specification.md` — cycle-accurate simulator behavior
- `specification/testbench-specification.md` — testbench language and execution model
- `specification/chip-info-specification.md` — chip data file format
- `specification/jzw-specification.md` — JZW waveform format
- `pipeline/rule_coverage.md` — rule ID → test plan map (375 rules)
- `pipeline/test_*.md` — test plan documents (~90 files)
- `pipeline/dependancies.md`, `pipeline/prompts/**`

**Criteria scored against:**
- Completeness — does the spec cover every language feature the compiler implements?
- Consistency — do the 5 spec documents agree with each other, and with the compiler?
- Clarity — is the spec readable by someone new to the project?
- Authoritativeness — spec vs. implementation disagreements: which is treated as source of truth?
- Rule coverage — are the rules in `compiler/src/rules.c` all documented in `pipeline/`?
- Stale/dead references — e.g. `.jzon` vs. `.json` drift, broken links, outdated file names

**Rationale:**
The five core specification documents are comprehensive and technically detailed, with consistent cross-references and shared terminology — `jz-hdl-specification.md` is 6925 lines and covers the language end-to-end (Sections 1–10). However, there is a clear drift signal: `rule_coverage.md` claims 375 total rules but `compiler/src/rules.c` contains roughly 387 rule entries, meaning rules have been added without updating the coverage map. The JZW spec is marked "Draft" while the others are "Beta," which is a minor tone inconsistency. Test coverage is uneven: ~327 rules tested, ~15 "Unimplemented" (largely template/tristate), ~15 "Dead code" (multidimensional wires/regs), ~7 known bugs, ~5 untestable. The specs themselves are TODO/FIXME-free, but the 40+ `pipeline/rule_coverage.md` "Not Tested" entries indicate compiler drift from spec intent.

**Key measurements:**
- `jz-hdl-specification.md`: 6925 lines (verified), Sections 1–10 covering identifiers, literals, operators, module structure, assignments, projects, memory, global, compile-time checks, templates
- `simulation-specification.md`: ~775 lines, event-driven timing, jitter/drift, cycle-accurate execution
- `testbench-specification.md`: ~1093 lines, cycle-stepped simulation model distinct from `@simulation`
- `chip-info-specification.md`: ~973 lines; uses `.json` throughout (no `.jzon` drift in the spec itself — the drift is in `CLAUDE.md` only)
- `jzw-specification.md`: ~550 lines, SQLite schema with picosecond resolution; marked "Draft"
- `rule_coverage.md` distribution (approximate): Tested ≈327, Unimplemented ≈15, Dead code ≈15, Bug ≈7, Suppressed ≈4, Not Testable ≈5 / 375 claimed total — but `rules.c` has ≈387 entries, so 12 rules are undocumented in the coverage map
- 90 `pipeline/test_*.md` plan documents; spot-checked files (`test_1_1-identifiers.md`, `test_4_13-module_instantiation.md`, `test_2_2-signedness_model.md`, `test_10_1-template_purpose.md`) show structured rule-ID-traceable test matrices

**Needed before 1.0.0:**
- Reconcile the ~12-rule discrepancy between `rule_coverage.md` (375) and `rules.c` (~387). Either add the missing rules to the coverage map or delete them from `rules.c`.
- Resolve the 15 "Not Tested: Unimplemented" rules (including `AMBIGUOUS_REFERENCE`, `LATCH_SR_WIDTH_MISMATCH`, template-related): implement and test, or formally defer post-1.0 with a note in the spec.
- Resolve the 15 "Not Tested: Dead code" rules: exercise them or delete them.
- Elevate `jzw-specification.md` from "Draft" to "Beta"/stable, or explain in the spec itself why it remains draft at 1.0.
- Add a changelog or "last updated" section to each of the five spec documents so readers can tell when features were introduced or revised.
- Cross-check the x/z semantics between `jz-hdl-specification.md` §§1.6/2.1 and `simulation-specification.md` §2.5 for agreement on observability and tristate resolution.
- Add a feature-matrix index showing which features appear in which spec (jz-hdl vs. sim vs. testbench), so drift between them becomes visible at a glance.

**Surprising findings:**
- The specs are unusually precise about timing resolution (picoseconds throughout) and float handling, which is commendable but is not mentioned in any overview — a new reader would miss it.
- JZW is fully SQLite-based and explicitly designed for concurrent read during simulation (WAL mode) — a mature waveform-capture design decision that is not cross-referenced from `jz-hdl-specification.md` itself.
- The testbench spec (~1093 lines) is longer than the simulation spec (~775 lines) despite being positioned as the "simpler" cycle-stepped model — neither is a strict subset of the other, which should be explicitly documented.
